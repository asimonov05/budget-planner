# Локальный планировщик бюджета

Self-hosted приложение для месячного планирования, учета факта, целей и резервов. Все пользователи, сессии и бюджеты находятся в одной базе PostgreSQL; финансовые строки разделены обязательным `user_id` и PostgreSQL RLS. PostgreSQL работает во внутренней сети Docker Compose, интерфейс и API — в контейнере приложения. Для подсказки валютного курса нужен доступ backend к сайту Банка России; при его отсутствии курс можно ввести вручную.

Существующий бюджет владельца переносится в общую базу отдельным migration job. Перед обновлением сделайте внешнюю копию PostgreSQL по [инструкции](docs/backup-restore.md).

## Быстрый запуск

Требуются Docker Engine и Docker Compose v2.

```bash
cp .env.example .env
mkdir -m 700 .secrets
python3 -c 'from pathlib import Path; import secrets; [(Path(".secrets") / name).write_text(secrets.token_urlsafe(48) + "\n") for name in ("postgres-password", "postgres-runtime-password", "postgres-debug-admin-password")]'
chmod 644 .secrets/postgres-*-password .secrets/postgres-password
docker compose up -d --build
docker compose exec app python -m app.cli init-admin
```

Команда `init-admin` интерактивно запрашивает пароль. При обновлении уже заполненной базы её повторять не нужно. `.secrets` не попадает в Git; храните каталог с правами `700`. PostgreSQL не публикует порт на хост.

Сервис `migrate` применяет Alembic один раз до запуска `app`. Приложение проверяет ревизию схемы, доступность БД и ограничения runtime-роли, но не запускает миграции самостоятельно.

```bash
docker compose ps
curl --fail http://127.0.0.1:8082/api/v1/health/ready
```

Откройте <http://127.0.0.1:8082>.

## Где лежат данные

- Единая PostgreSQL база `budget`: пользователи, сессии и все бюджеты. Файлы PostgreSQL находятся в томе `budget-planner_postgres_data`.
- Приложение записывает только временные файлы в ограниченный `tmpfs` `/tmp`. У него нет тома физических резервных копий.

Обычные `stop`, `restart`, `up -d --build` и `down` сохраняют том PostgreSQL. `docker compose down -v` удаляет финансовые данные. Том сам по себе не является резервной копией: делайте внешнюю копию и проверяйте восстановление.

## Владелец и пароль

Ссылка на самостоятельную регистрацию находится на экране входа; создание аккаунтов разрешается после локальной настройки владельца. Любой, у кого есть доступ к адресу приложения, может создать отдельный личный бюджет: логин — от 3 до 80 символов латиницей, пароль — не менее 12 символов. Зарегистрированный пользователь не получает права владельца. Первый владелец создаётся локально после первой миграции; его пароль можно сбросить:

```bash
docker compose exec app python -m app.cli init-admin
docker compose exec app python -m app.cli reset-password
```

Владелец управляет дополнительными пользователями в «Настройки → Пользователи»: создаёт логин и пароль, отключает доступ и задаёт новый пароль. Каждый пользователь видит только свои финансы и настройки. Для повторного импорта собственного ZIP пользователь может открыть «Настройки → Основные» и сбросить бюджет с текущим паролем и фразой `RESET`; учётная запись и текущая сессия сохраняются. Полного self-service удаления учётной записи пока нет.

## Отладочная админка

Включение: `DEBUG_ADMIN_ENABLED=1` в `.env`, затем `docker compose up -d app`. Панель `/admin/` доступна только активному владельцу (`is_admin`); при выключенном флаге она отвечает `404`. Панель читает модели через отдельную PostgreSQL роль `debug_admin` и предназначена только для диагностики. Её роль имеет `SELECT`, но не права на финансовые изменения. Обычный API всегда использует ограниченную роль `budget_runtime` с RLS-контекстом владельца.

## Изменение, архив и удаление

В списках счетов, категорий, тегов, целей, кредитов, планов и операций есть действия «Изменить», «Архивировать/восстановить» и «Удалить». Для кредита карточка редактируется в разделе «Кредиты», а неоплаченные строки — в его графике.

В разделе «Счета» показаны текущие остатки каждого счёта и итоги отдельно по каждой валюте, включая архивные счета. Общего пересчитанного итога нет. Остаток считается на текущую дату в часовом поясе бюджета: операции и переводы с будущей датой появятся в нём только в свой день. Создание, изменение и архивирование счетов доступны по кнопке «Управлять счетами»; при создании можно выбрать валюту счёта. Перевод между счетами — на странице «Операции». Для межвалютного перевода укажите фактический курс: форма заранее покажет сумму зачисления в валюте второго счёта.

При оплате в валюте, отличной от валюты счёта, выберите валюту покупки и укажите курс. Основная сумма операции показывается в валюте покупки, под ней — изменение остатка счёта в его валюте. В «Настройки → Валюты» можно посмотреть ориентировочный курс Банка России на дату; при оформлении операции он предлагается автоматически. Курс банка при фактическом списании может отличаться, поэтому его можно изменить вручную. Балансы и прогнозы отображаются отдельно по валютам. Цели, кредиты, лимиты и зарплата пока используют основную валюту бюджета; обычные плановые платежи могут быть в валюте своего счёта.

Для кредита можно задать годовую ставку, выбрать простые или сложные проценты и расчётный аннуитетный график. В графике показаны регулярный платёж, будущие проценты, погашение основного долга и остаток после каждого платежа. Сценарий досрочного погашения показывает два варианта: сохранить платёж и сократить срок либо сохранить конечную дату и уменьшить платёж. Это расчётный прогноз по фактическим дням; сверяйте его с договором и графиком банка. Ручной график остаётся доступен.

Плановый платёж можно связать с кредитом в разделе «Платежи и расходы», фактический — при создании операции или позже через действие «Связать с кредитом». Для старой операции укажите, учтена ли она уже в текущем остатке долга; такую информационную связь можно снять без изменения денег. Факт по ручному графику проводится из карточки кредита. При наличии кредитного графика связанный с ним плановый платёж не добавляется в прогноз второй раз.

Чтобы изменить постоянный доход или платёж на одну дату, откройте «Календарь» и нажмите на событие. Можно поменять сумму, перенести дату в другой месяц или вернуть значения повторяющейся серии. Остальные месяцы не меняются; сверенное с фактом или закрытое повторение редактировать нельзя.

Для оценки регулярных трат отметьте расходную категорию в «Настройки → Категории» пунктом «Оценивать расход каждый месяц». «План на год» использует средний расход за три завершённых месяца, включая месяцы без трат, и показывает добавленную к прогнозу часть отдельной строкой. Уже учтённые фактические траты, планы и лимиты второй раз не прибавляются; оценка уменьшает прогноз свободных денег для целей.

Для зарплаты до налога откройте «Настройки → Зарплата», включите расчёт и создайте отдельное правило для каждого работодателя. Укажите месячную сумму до НДФЛ, долю аванса, дни аванса и зарплаты, счёт и месяц начала. В выплатах и календаре появятся суммы после НДФЛ; план учитывает их на фактические даты с переносом с выходного или федерального праздника на предыдущий рабочий день. Если обычный повторяющийся доход уже создан, вручную отключите его на странице «Доходы», иначе прогноз посчитает оба плана. Фактическое поступление можно связать с расчётной выплатой на вкладке зарплаты, чтобы исключить двойной учёт. Для начала учёта посреди года укажите уже начисленную у работодателя сумму с начала года до первой рассчитываемой выплаты.

Физическое удаление разрешено только для несвязанной записи без истории. Если есть операции, платежи, резервы или другие связи, API вернёт `409`, а интерфейс предложит архивирование. Кредит с непогашенными строками графика нельзя скрыть в архив до их оплаты или отмены; для дальнейшего изменения графика архивный кредит сначала нужно восстановить.

## Темы интерфейса

В разделе «Настройки → Оформление» доступны светлая, тёмная и системная темы. Системный режим автоматически следует за настройкой операционной системы или браузера без перезагрузки страницы. Независимо от яркости можно выбрать одну из четырёх цветовых схем: «Лес», «Океан», «Слива» или «Янтарь».

Там же можно выбрать шрифт: классическое сочетание системного текста и заголовков Georgia либо Golos Text для всего интерфейса. Все три выбора хранятся в `localStorage` текущего браузера, не попадают в финансовую базу и не переносятся через экспорт проекта. Тема, цветовая схема и шрифт применяются до запуска React.

## Резервное копирование и восстановление

Физический backup PostgreSQL выполняется вне backend через `pg_dump`. Он содержит все бюджеты и учётные записи; кнопки backup/restore в приложении нет. Команды и процедура проверки восстановления приведены в [docs/backup-restore.md](docs/backup-restore.md). Канонический ZIP в разделе «Импорт/экспорт» переносит только финансовые данные одного пользователя.

## Импорт и экспорт

В интерфейсе откройте «Импорт/экспорт». Импорт всегда двухфазный: загрузка и настройка → предпросмотр ошибок/дублей → явное подтверждение. До подтверждения бюджет не меняется.

Поддерживаются:

- фактические операции;
- разовые и повторяющиеся плановые доходы/расходы;
- график существующего кредита.

Готовые файлы и справочные шаблоны находятся в [examples/imports](examples/imports). Мастер P0 сейчас принимает только `transactions.csv`, `plan-items.csv` и `loan-schedule.csv`; лимиты и взносы целей переносятся каноническим ZIP. Подробные колонки, кодировки, разделители, ограничения и правила дублей описаны в [docs/csv-format.md](docs/csv-format.md). Неоднозначные даты требуют ручного выбора формата.

Есть два разных экспорта: безопасный читаемый CSV для табличного редактора и канонический ZIP-перенос проекта. Полный `.dump` не заменяет перенос, а ZIP-перенос не содержит пароль и активные сессии.

## Обновление и откат

Перед обновлением сохраните внешний PostgreSQL dump по [инструкции](docs/backup-restore.md) и копию текущего образа. После этого:

```bash
docker image tag budget-planner:local budget-planner:before-update
docker compose up -d --build
```

Compose запускает `migrate`, ожидает успешного завершения и только затем запускает API. Не открывайте новую схему старым образом. Для отката сначала восстановите совместимый dump, затем запустите соответствующий старый образ.

## Доступ из LAN

По умолчанию порт привязан только к `127.0.0.1`. Для домашней сети укажите в `.env` конкретный адрес сервера и разрешенные Host-заголовки:

```dotenv
BIND_HOST=192.168.1.10
TRUSTED_HOSTS=192.168.1.10,budget.home
SESSION_COOKIE_SECURE=0
FORWARDED_ALLOW_IPS=127.0.0.1
```

`TRUSTED_HOSTS` содержит только имена/IP из HTTP-заголовка `Host`, без схемы и пути. `BIND_HOST` должен быть адресом интерфейса именно этого сервера, а не `0.0.0.0`, если в этом нет необходимости. Прямой HTTP-доступ из доверенной домашней сети оставляет secure-cookie выключенной.

Для HTTPS reverse proxy на том же хосте оставьте backend на loopback и задайте внешний host и точный адрес, с которого приложение видит прокси:

```dotenv
BIND_HOST=127.0.0.1
TRUSTED_HOSTS=budget.example.net
SESSION_COOKIE_SECURE=1
FORWARDED_ALLOW_IPS=127.0.0.1
```

Если прокси приходит не с loopback, замените `FORWARDED_ALLOW_IPS` его конкретным IP или доверенной подсетью. Не ставьте `*`: Uvicorn использует этот список, чтобы решать, от кого принимать `X-Forwarded-*`; эти заголовки влияют в том числе на проверку `Origin` для изменяющих запросов. Прокси должен передавать исходный `Host`, `X-Forwarded-Proto: https` и не публиковать внутренние сервисы PostgreSQL. Не открывайте порт приложения напрямую в интернет.

## Разработка и проверки

Поддерживаемое окружение разработки: uv, Python 3.13 и Node.js 22. Создайте окружение из `pyproject.toml` и зафиксированного `uv.lock`:

```bash
uv sync --locked --project backend
npm --prefix frontend ci
npm --prefix e2e ci
npx --prefix e2e playwright install chromium
```

`uv sync` создаёт окружение в `backend/.venv` и устанавливает runtime- и dev-зависимости из `backend/uv.lock`. Frontend и E2E используют отдельные `package-lock.json`.

Ревизии Alembic уже зафиксированы до `0008`. Новые изменения схемы оформляйте новой ревизией и одновременно обновляйте [ER-диаграмму](docs/database-schema.excalidraw). Исторические SQLite-тесты остаются переходным долгом [TD-003](docs/technical-debt.md); рабочий Compose использует PostgreSQL.

Основные проверки:

```bash
make lint
make test
make build
make test-e2e       # нужен уже запущенный production-style сервер
make acceptance     # поднимает отдельный Compose project и запускает E2E
```

Playwright всегда выполняет гостевые сценарии входа; authenticated smoke включается только при заданных `E2E_USERNAME` и `E2E_PASSWORD`. Подробности и правила фиксации результата — в [docs/acceptance.md](docs/acceptance.md); [статус приемки](docs/acceptance-status.md) относится к прежнему SQLite-развёртыванию. Архитектура описана в [docs/architecture.md](docs/architecture.md), формулы — в [docs/calculation-rules.md](docs/calculation-rules.md), решения — в [docs/decisions.md](docs/decisions.md).

Docker-образ multi-stage: Node используется только для сборки SPA. Runtime работает непривилегированным UID 10001, с read-only root filesystem и без Linux capabilities. Рабочая база — PostgreSQL. Оставшиеся SQLite-ветки и подготовка к нескольким репликам перечислены в [реестре технического долга](docs/technical-debt.md).

Целевые архитектуры образа: `linux/amd64` и `linux/arm64`. Не считайте их проверенными, пока соответствующие строки smoke-проверки не отмечены в acceptance-статусе.
