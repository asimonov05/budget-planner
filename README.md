# Локальный планировщик бюджета

Self-hosted приложение для месячного планирования, учета факта, целей и резервов. Финансовые данные хранятся в SQLite на вашем диске; React-интерфейс и API работают из одного контейнера. Внешний интернет после сборки не нужен.

Текущие локальные прогоны подтверждают 74 backend-теста и 54 frontend-теста. Четыре live Playwright-сценария и изолированный Compose-drill были пройдены ранее: они подтвердили `init-admin`, SQLite 3.53.4, UID 10001, read-only root, persistence после `force-recreate` и restore с отзывом старых сессий. Канонический ZIP проходит round-trip. Из-за локального DNS-сбоя Docker Hub финальный drill использовал финальные code/static слои поверх ранее полностью собранного runtime; чистая повторная multi-stage сборка последнего дерева осталась непроверенной. Точные границы — в [статусе приемки](docs/acceptance-status.md).

## Быстрый запуск

Требуются Docker Engine и Docker Compose v2.

```bash
cp .env.example .env
docker compose build
docker compose run --rm app python -m app.cli init-admin
docker compose up -d
```

Если первая сборка прервалась на `npm ci` с `ETIMEDOUT`, повторите `docker compose build`: уже скачанные tarball сохраняются в BuildKit cache. Dockerfile настраивает пять сетевых повторов, увеличенный timeout и `--prefer-offline`, не отключая проверку `package-lock.json`. Audit-запрос отключен только внутри build-шага; его можно запустить отдельно командой `npm --prefix frontend audit`.

Откройте <http://127.0.0.1:8082>. Команда `init-admin` интерактивно запрашивает пароль: не передавайте пароль аргументом или переменной окружения. При повторном запуске используется существующая база.

Проверка состояния:

```bash
docker compose ps
docker compose logs --tail=100 app
curl --fail http://127.0.0.1:8082/api/v1/health/ready
```

Контейнер автоматически применяет миграции до приема запросов. Production-процесс один: это намеренный профиль работы с SQLite.

## Где лежат данные

- база: `/data/budget.sqlite3` в named volume `budget-planner_budget_data`;
- WAL/SHM SQLite: рядом с базой в том же каталоге `/data`;
- физические резервные копии: `/backups` в volume `budget-planner_budget_backups`;
- временные файлы: ограниченный `tmpfs` `/tmp`.

`docker compose stop`, `restart`, `up -d --build`, пересоздание контейнера и обычный `docker compose down` не удаляют volumes. Команда `docker compose down -v` удаляет оба тома и финансовые данные — выполняйте ее только при осознанном полном сбросе после выноса проверенного бэкапа.

Сам volume не является бэкапом. Оба тома обычно находятся на одном диске и не защищают от его отказа.

## Владелец и пароль

Открытой регистрации нет. Создание владельца и сброс пароля выполняются локально:

```bash
docker compose run --rm app python -m app.cli init-admin
docker compose run --rm app python -m app.cli reset-password
```

Сессии и финансовые API защищены приложением. При краже диска файл SQLite не шифруется паролем приложения: используйте шифрование диска и права файловой системы.

## Отладочная админка

Владелец может включить отдельную Django-подобную админку переменной `DEBUG_ADMIN_ENABLED=1` в `.env`. Пересоберите и запустите приложение командой `docker compose up -d --build`, затем откройте `/admin/` или выберите «Админка» в меню. Для входа используйте логин и пароль владельца. По умолчанию админка выключена; при выключенном флаге `/admin/` возвращает `404`.

Админка работает с SQLAlchemy-моделями напрямую: позволяет искать, просматривать, создавать, изменять и удалять записи. Столбцы с паролями, токенами и хешами скрыты; владелец и журнал аудита доступны только для просмотра. Изменения из админки обходят бизнес-валидацию финансового API, поэтому используйте её для отладки. Действия админки записываются в журнал аудита.

## Изменение, архив и удаление

В списках счетов, категорий, тегов, целей, кредитов, планов и операций есть действия «Изменить», «Архивировать/восстановить» и «Удалить». Для кредита карточка редактируется в разделе «Кредиты», а неоплаченные строки — в его графике.

Для кредита можно задать годовую ставку, выбрать простые или сложные проценты и расчётный аннуитетный график. В графике показаны регулярный платёж, будущие проценты, погашение основного долга и остаток после каждого платежа. Сценарий досрочного погашения показывает два варианта: сохранить платёж и сократить срок либо сохранить конечную дату и уменьшить платёж. Это расчётный прогноз по фактическим дням; сверяйте его с договором и графиком банка. Ручной график остаётся доступен.

Плановый платёж можно связать с кредитом в разделе «Платежи и расходы», фактический — при создании операции или позже через действие «Связать с кредитом». Для старой операции укажите, учтена ли она уже в текущем остатке долга; такую информационную связь можно снять без изменения денег. Факт по ручному графику проводится из карточки кредита. При наличии кредитного графика связанный с ним плановый платёж не добавляется в прогноз второй раз.

Чтобы изменить постоянный доход или платёж на одну дату, откройте «Календарь» и нажмите на событие. Можно поменять сумму, перенести дату в другой месяц или вернуть значения повторяющейся серии. Остальные месяцы не меняются; сверенное с фактом или закрытое повторение редактировать нельзя.

Для оценки регулярных трат отметьте расходную категорию в «Настройки → Категории» пунктом «Оценивать расход каждый месяц». «План на год» использует средний расход за три завершённых месяца, включая месяцы без трат, и показывает добавленную к прогнозу часть отдельной строкой. Уже учтённые фактические траты, планы и лимиты второй раз не прибавляются; оценка уменьшает прогноз свободных денег для целей.

Физическое удаление разрешено только для несвязанной записи без истории. Если есть операции, платежи, резервы или другие связи, API вернёт `409`, а интерфейс предложит архивирование. Кредит с непогашенными строками графика нельзя скрыть в архив до их оплаты или отмены; для дальнейшего изменения графика архивный кредит сначала нужно восстановить.

## Темы интерфейса

В разделе «Настройки → Оформление» доступны светлая, тёмная и системная темы. Системный режим автоматически следует за настройкой операционной системы или браузера без перезагрузки страницы. Независимо от яркости можно выбрать одну из четырёх цветовых схем: «Лес», «Океан», «Слива» или «Янтарь».

Там же можно выбрать шрифт: классическое сочетание системного текста и заголовков Georgia либо Golos Text для всего интерфейса. Все три выбора хранятся в `localStorage` текущего браузера, не попадают в финансовую базу и не переносятся через экспорт проекта. Тема, цветовая схема и шрифт применяются до запуска React.

## Резервное копирование и восстановление

Создать консистентную копию работающей WAL-базы через SQLite Online Backup API:

```bash
docker compose exec app python -m app.cli backup
```

Команда печатает имя созданного файла. Вынесите его на другой носитель, например:

```bash
docker compose cp app:/backups/ИМЯ_КОПИИ.sqlite3 ./ИМЯ_КОПИИ.sqlite3
```

Восстановление выполняется только при остановленном основном приложении:

```bash
docker compose stop app
docker compose run --rm app python -m app.cli restore /backups/ИМЯ_КОПИИ.sqlite3
docker compose up -d
```

CLI проверяет целостность, внешние ключи и известную версию схемы, сохраняет заменяемую базу отдельно и отзывает старые сессии. Не заменяйте `budget.sqlite3` обычным `cp` при работающем приложении: WAL может содержать актуальные страницы. Полная процедура и пример внешнего cron — в [docs/backup-restore.md](docs/backup-restore.md).

## Импорт и экспорт

В интерфейсе откройте «Импорт/экспорт». Импорт всегда двухфазный: загрузка и настройка → предпросмотр ошибок/дублей → явное подтверждение. До подтверждения бюджет не меняется.

Поддерживаются:

- фактические операции;
- разовые и повторяющиеся плановые доходы/расходы;
- график существующего кредита.

Готовые файлы и справочные шаблоны находятся в [examples/imports](examples/imports). Мастер P0 сейчас принимает только `transactions.csv`, `plan-items.csv` и `loan-schedule.csv`; лимиты и взносы целей переносятся каноническим ZIP. Подробные колонки, кодировки, разделители, ограничения и правила дублей описаны в [docs/csv-format.md](docs/csv-format.md). Неоднозначные даты требуют ручного выбора формата.

Есть два разных экспорта: безопасный читаемый CSV для табличного редактора и канонический ZIP-перенос проекта. Физический SQLite-бэкап не заменяет перенос, а ZIP-перенос не содержит пароль и активные сессии.

## Обновление и откат

Перед обновлением сначала создайте и вынесите бэкап:

```bash
docker compose exec app python -m app.cli backup
docker image tag budget-planner:local budget-planner:before-update
docker compose up -d --build
```

В `compose.yaml` образ имеет тег `budget-planner:${APP_IMAGE_TAG:-local}`. Чтобы откатить код, остановите приложение, восстановите совместимый бэкап, созданный до миграции, укажите `APP_IMAGE_TAG=before-update` в `.env` и запустите:

```bash
docker compose stop app
# восстановите предмиграционный бэкап командой из раздела выше
docker compose up -d --no-build
```

Не открывайте новую схему старой версией приложения. Обычный rebuild не удаляет данные.

## Доступ из LAN

По умолчанию порт привязан только к `127.0.0.1`. Для домашней сети укажите в `.env` конкретный адрес сервера и разрешенные Host-заголовки:

```dotenv
BIND_HOST=192.168.1.10
TRUSTED_HOSTS=192.168.1.10,budget.home
SESSION_COOKIE_SECURE=0
FORWARDED_ALLOW_IPS=127.0.0.1
```

`TRUSTED_HOSTS` содержит только имена/IP из HTTP-заголовка `Host`, без схемы и пути. `BIND_HOST` должен быть адресом интерфейса именно этого сервера, а не `0.0.0.0`, если в этом нет необходимости. Прямой HTTP-доступ из доверенной домашней сети оставляет secure-cookie выключенной.

Для HTTPS reverse proxy на том же хосте оставьте backend на loopback и задайте внешний host и точный адрес, с которого приложение видит прокси:

```dotenv
BIND_HOST=127.0.0.1
TRUSTED_HOSTS=budget.example.net
SESSION_COOKIE_SECURE=1
FORWARDED_ALLOW_IPS=127.0.0.1
```

Если прокси приходит не с loopback, замените `FORWARDED_ALLOW_IPS` его конкретным IP или доверенной подсетью. Не ставьте `*`: Uvicorn использует этот список, чтобы решать, от кого принимать `X-Forwarded-*`; эти заголовки влияют в том числе на проверку `Origin` для изменяющих запросов. Прокси должен передавать исходный `Host`, `X-Forwarded-Proto: https` и не публиковать `/data` или `/backups`. Не открывайте порт приложения напрямую в интернет.

## Разработка и проверки

Поддерживаемое окружение разработки: Python 3.13 и Node.js 22. Создайте чистое окружение из зафиксированных lock-файлов:

```bash
python3.13 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
npm --prefix frontend ci
npm --prefix e2e ci
npx --prefix e2e playwright install chromium
```

`requirements-dev.txt` включает полностью закрепленный production-набор из `requirements.lock`; оба npm-проекта устанавливаются через свои `package-lock.json`.

Схема `0001` зафиксирована в `backend/alembic/versions/0001_initial.py`. При изменении моделей добавляйте следующую ревизию Alembic с явными операциями изменения схемы; не меняйте уже применённую `0001`. Проверка `backend/tests/test_migrations.py` сверяет новую базу с моделями и проверяет обновление базы с существующей ревизией `0001`.

Основные проверки:

```bash
make lint
make test
make build
make test-e2e       # нужен уже запущенный production-style сервер
make acceptance     # поднимает отдельный Compose project и запускает E2E
```

Playwright всегда выполняет гостевые сценарии входа; authenticated smoke включается только при заданных `E2E_USERNAME` и `E2E_PASSWORD`. Подробности, локальный запуск backend/frontend и правила фиксации результата — в [docs/acceptance.md](docs/acceptance.md). Текущий подтвержденный статус — в [docs/acceptance-status.md](docs/acceptance-status.md). Архитектурные ограничения зафиксированы в [docs/architecture.md](docs/architecture.md), формулы — в [docs/calculation-rules.md](docs/calculation-rules.md), принятые решения — в [docs/decisions.md](docs/decisions.md).

Docker-образ multi-stage: Node используется только для сборки SPA, в runtime его нет. Runtime работает непривилегированным UID 10001, с read-only root filesystem, без Linux capabilities. На старте проверяется версия `sqlite3`, реально загруженная Python; требуется не ниже 3.51.3.

Целевые архитектуры образа: `linux/amd64` и `linux/arm64`. Не считайте их проверенными, пока соответствующие строки smoke-проверки не отмечены в acceptance-статусе.
