# ADR-009: администрирование и доступность приложений в супераппе

Статус: принято. Дата: 2026-10-15.

По запросу владельца управление всеми данными переносится в суперапп.
Эта запись заменяет положение ADR-002 об отдельной диагностической панели
под `DEBUG_ADMIN_ENABLED`. Обычный пользовательский API сохраняет изоляцию
по текущему пользователю.

## Решение

Единая сессия и `users.is_admin` дают доступ к `/admin/` и административным
API. Общий вход и админка остаются доступны при закрытых приложениях.
`application_availability` хранит глобальные правила, `user_app_access` —
версионируемые пользовательские исключения. Отсутствующее/пустое исключение
наследует глобальное правило; явное разрешение или запрет имеет приоритет.
Флаги развёртывания по-прежнему закрывают неработающие сервисы на шлюзе.

API финансовых маршрутов проверяет доступность бюджета, фото проверяет
идентичность и доступ одним вызовом центрального backend. Правила проверяются
в БД на каждом запросе, включая существующие пользовательские сессии.
Роль администратора не даёт обхода правил использования приложения.

Каталог админки включает все прикладные таблицы из SQLAlchemy metadata.
Структура таблиц, первичные ключи и ссылки видны; свободный текст, JSON,
персональные даты, суммы и секреты маскируются сервером по принципу закрытого
доступа по умолчанию. Поиск скрытого значения и сортировка по нему запрещены.
Разрешённые личные поля имеют форму ввода замены без чтения оригинала.

По запросу владельца от 16 октября 2026 отдельное скрытое поле можно
временно раскрыть глазком в таблице или карточке записи. Обычные list/detail
ответы остаются замаскированными. Раскрытие использует отдельный POST с
проверкой текущей административной роли, CSRF и Origin; сервер возвращает
только явно выбранное поле из проверенного списка. Новые поля не получают
разрешение автоматически. Пароли, токены, хеши и служебный JSON не
раскрываются. Аудит фиксирует актора, запись и имя поля без его значения.
Раскрытое значение не заполняет поле ввода замены и не включается в PATCH.
При повторном нажатии, смене раздела/записи, закрытии карточки, уходе со
страницы или скрытии вкладки браузер удаляет раскрытые значения; запоздалые
ответы не восстанавливают их. Клиент не сохраняет значения в storage.

Чтение всех владельцев использует отдельную роль `debug_admin` только с
SELECT и явными RLS-политиками. Записи используют `budget_runtime` без DDL,
владения таблицами и BYPASSRLS: сервер устанавливает проверенный контекст
администратора и выбранного владельца, берёт его финансовую advisory lock,
проверяет ревизию и сохраняет изменение вместе с аудитом. Пользовательские
ID из обычных API не меняют scope. Служебные и связанные финансовые сущности
сохраняют защиту от обхода предметных операций.

Старый SQLAdmin backend не монтируется даже при старом debug-флаге.
Ответы административных API имеют `Cache-Control: no-store`; аудит хранит
акторов, идентификаторы и названия изменённых полей без значений.

## Ограничения

Админка управляет прикладными таблицами общей базы; служебная таблица Alembic
не является редактируемой моделью. Photo-access сейчас не содержит собственной
БД или объектов хранилища. Публикация уведомлений, изменение связанных платежей
и другие составные действия выполняются через соответствующие предметные
сценарии, чтобы не нарушить согласованность данных.

Ревизия карточки — HMAC снимка с ключом процесса. После перезапуска backend
открытую карточку нужно загрузить заново. Поддержка нескольких backend-реплик
остаётся частью TD-002 и требует общего ключа ревизий или версии всех строк.
