# ADR-002: монолитный backend и отдельная БД

**Статус:** принято для монолита, требования multi-deployment, migration job,
login rate limit на reverse proxy, PostgreSQL-only и общей БД с server-side
`user_id` scope, user-scoped уникальностью и PostgreSQL RLS; оставшиеся детали
rollout требуют отдельного согласования. Модель делегированного доступа пока
не вводится. RLS-контекст задаётся через `SET LOCAL` в транзакции; migration и
runtime используют отдельные PostgreSQL-роли; debug-admin использует третью
изолированную роль. Финансовая блокировка scoped по `user_id`.

**Слой:** backend / deployment.

## Решение

Backend — один сервис FastAPI. Он владеет HTTP API, авторизацией, бизнес-правилами
финансовой модели, Alembic-миграциями и раздачей собранного SPA. Финансовые
данные хранятся в PostgreSQL, доступном приложению только по внутренней сети
Compose; порт БД не публикуется на хост.

Сейчас приложение запускается одной репликой и одним Uvicorn worker, но это
не архитектурный предел. Backend должен быть совместим с несколькими
экземплярами за reverse proxy: ни один финансовый инвариант или API-контракт
не может полагаться на память конкретного процесса или его локальную файловую
систему.

## Техническая реализация backend

### Жизненный цикл и развёртывание

Текущая однорепличная поставка запускает Alembic-миграции перед HTTP-сервером.
Для multi-deployment принят следующий порядок:

1. отдельный синхронный Alembic migration job применяет миграции ровно один
   раз через sync API `psycopg` 3;
2. экземпляры backend запускаются только после успешной миграции;
3. каждый экземпляр проверяет доступность БД и её обязательные настройки;
4. `GET /api/v1/health/live` проверяет процесс, а
   `GET /api/v1/health/ready` — соединение с БД.

Тесты используют disposable PostgreSQL. Каждый test suite поднимает временный
сервер, а каждый parallel worker получает изолированную БД или схему; Alembic
применяется до тестов. Runtime тестов использует тот же async стек, что и API;
SQLite-fixtures не поддерживаются.

### HTTP-граница

Все прикладные маршруты находятся под `/api/v1` и сгруппированы по областям:
auth, каталог, финансы, зарплата, пользователи и import/export. Backend
устанавливает `X-Request-ID`, безопасные заголовки, `TrustedHostMiddleware` и
единый формат ошибок. Запросы к несуществующим API-маршрутам не попадают в SPA
fallback.

### Доступ к данным и транзакции

- SQLAlchemy — единственный слой доступа к данным; модель и Alembic задают
  схему.
- PostgreSQL — единственное поддерживаемое хранилище во всех средах и общий
  источник состояния между экземплярами. Локальная разработка и тесты также
  используют изолированный PostgreSQL; SQLite не поддерживается.
- Все пользователи используют одну PostgreSQL БД. Пользователь и его
  финансовые данные находятся в одной БД, поэтому `user_id` может быть
  обязательным внешним ключом, а не недоказуемым идентификатором из другой
  БД.
- Для финансовой мутации CSRF-защищённый запрос резервирует слот записи:
  PostgreSQL advisory transaction lock, scoped по `user_id` и общий для всех
  экземпляров этого пользователя.
- Версионные сущности используют optimistic locking через поле `version`;
  конфликт обновления возвращается как HTTP 409.

### Изоляция данных

Каждая финансовая сущность и user-scoped служебная сущность принадлежит
пользователю через обязательный `user_id`. Backend получает владельца только
из аутентифицированной сессии; он не принимает `user_id` или имя tenant-БД от
клиента как основание для доступа.

Все чтения, изменения, агрегаты, уникальные ограничения и внешние ключи
должны учитывать этот scope. В частности, клиент не может получить или
изменить запись другого пользователя, зная её числовой `id`. Точная модель
составных уникальных ключей принята: естественные идентификаторы справочников
уникальны в пределах владельца, например `(user_id, name)` для категорий и
тегов. Любые внешние идентификаторы операций и idempotency keys также scoped
по `user_id`, например `(user_id, key)`.

Совместный бюджет, делегированный доступ и произвольная модель ролей пока не
поддерживаются. В обычном пользовательском API финансовые данные доступны
только владельцу. Единственное исключение — диагностическая debug-admin
панель: она доступна только owner (`is_admin`) при явном
`DEBUG_ADMIN_ENABLED=1`; для остальных пользователей и при выключенной
переменной она не показывается и отвечает 404. Любое другое исключение
потребует отдельной модели прав и ADR.

Канонический ZIP принадлежит одному пользователю: экспорт включает только его
user-scoped данные, а импорт разрешён только в его пустой финансовый контур.
Для повторного импорта пользователь может сбросить собственные финансовые и
user-scoped служебные данные, не удаляя логин, пароль или учётную запись. Эта
операция всегда scoped по текущей сессии. Она требует текущий пароль и фразу
`RESET`, выполняется одной транзакцией и фиксируется отдельным audit-событием.
Все остальные сессии владельца отзываются; текущая сохраняется для
немедленного ZIP-import.

Полное self-service удаление учётной записи пока не поддерживается. Reset
финансовых данных покрывает переимпорт, а окончательное удаление identity,
владельца системы и истории требует отдельной политики и ADR.

Изоляция обеспечивается двумя слоями. Backend всегда добавляет server-side
`user_id` scope к запросу. PostgreSQL Row-Level Security (RLS) дублирует это
правило на уровне БД и не позволяет ошибочному запросу прочитать или изменить
чужую строку. RLS применяется к финансовым и user-scoped служебным таблицам;
политики и роль приложения не должны позволять bypass этой защиты.

Перед первым доступом к user-scoped данным backend открывает транзакцию и
устанавливает `user_id` из сессии через `SET LOCAL`. RLS-политики читают только
этот transaction-local контекст. При commit, rollback или возврате соединения
в пул значение автоматически сбрасывается, поэтому scope одного запроса не
может попасть в следующий.

Для миграций используется отдельная роль, имеющая права DDL. Runtime-роль
приложения не владеет таблицами, не имеет `BYPASSRLS` и получает только нужные
DML-права. На user-scoped таблицах включается `FORCE ROW LEVEL SECURITY`, чтобы
владение таблицей не стало обходом политик.

Debug-admin не использует runtime-роль и не становится доступным обычному
пользовательскому API. Он использует отдельную PostgreSQL `debug_admin`-роль:
RLS-политики явно дают ей диагностический доступ ко всем строкам, не прибегая
к `BYPASSRLS`. Соединение с этой ролью создаётся только для панели после
owner-аутентификации и при включённом `DEBUG_ADMIN_ENABLED`; UI-ссылка остаётся
недоступной всем остальным.

### Авторизация и изоляция данных

Пароль хранится как Argon2 hash. Браузер получает только cookie с сессионным
токеном; в БД хранится его SHA-256 hash и отдельный hash CSRF-токена.
Финансовая сессия получает `user_id` только из записи аутентифицированного
пользователя — имя БД и scope владельца не принимаются от клиента. Изменяющие
запросы требуют CSRF-токен и same-origin проверку.

Сессии уже хранятся в БД и потому доступны любому экземпляру backend. Login
rate limit обеспечивается reverse proxy до FastAPI с единой политикой для всех
реплик. Любое другое общее состояние — очередь, lock вне транзакции, кэш с
влиянием на корректность — должно находиться во внешнем shared-компоненте или
в PostgreSQL, а не в памяти процесса.

### Контейнер и статика

SPA собирается Node на build-стадии Docker и копируется в Python runtime.
FastAPI раздаёт `/assets` и `index.html`, поэтому для пользователя UI и API
имеют один origin. Runtime работает непривилегированным пользователем и с
read-only root filesystem; доступ на запись ограничен рабочими каталогами.

### Слоистая архитектура backend

Backend развивается как трёхслойная архитектура с направлением зависимостей
из presentation через application к infrastructure:

```text
presentation → application → infrastructure
```

- **Presentation / transport** — FastAPI routers, Pydantic-схемы, CLI и
  HTTP-обработчики. Этот слой отвечает за аутентификацию, валидацию формата,
  преобразование HTTP в command/query и HTTP-ответ. Он не содержит финансовых
  правил, SQLAlchemy-запросов и `commit`.
- **Application** — use cases, команды/запросы и прямые entity handlers. Этот
  слой передаёт owner context из сессии, применяет авторизационные правила,
  содержит финансовые правила, расчёты, инварианты и value objects, а также
  работает с абстракциями репозиториев. Application не импортирует FastAPI,
  SQLAlchemy, HTTP, конфигурацию или детали хранения.
- **Infrastructure** — SQLAlchemy-модели, PostgreSQL, реализации репозиториев,
  Alembic, ZIP-адаптеры, reverse-proxy интеграции и другие внешние механизмы.
  Инфраструктура реализует порты application-слоя, а не задаёт бизнес-правила.

Application-слой определяет нужные ему интерфейсы репозиториев, а
infrastructure предоставляет реализации. Presentation собирает зависимости,
но не передаёт user/tenant scope из данных клиента: owner context создаётся
только из аутентифицированной сессии.

Repository ports предметные и узкие: они выражают потребности операций,
планирования, прогноза и других application-сценариев. Универсальный
`GenericRepository` не вводится. Порты не возвращают и не принимают
SQLAlchemy-модели как application-контракт.

Подключение к данным передаётся через dependency injection: presentation
получает application handler/use case и Unit of Work из composition root, а
application получает порты репозиториев и транзакции через интерфейсы. Прямой
доступ к module-global engine или `Session` за пределами infrastructure
запрещён.

FastAPI `Depends` — принятый механизм DI в presentation. Для любого
application- или infrastructure-класса создаётся provider/stub, который
собирает его зависимости и передаёт готовый объект обработчику. В HTTP-тестах
такой provider подменяется через `dependency_overrides`; вне HTTP класс можно
создать с test double явно. Это не требует импортировать `Depends` внутрь
application-класса и сохраняет его переносимость в CLI и unit-тесты.

Engine и connection pool — долгоживущие infrastructure-зависимости уровня
процесса. Backend использует SQLAlchemy `AsyncEngine` и `AsyncSession` с
async dialect драйвера `psycopg` 3; presentation dependencies и I/O-bound
application handlers являются `async`.
`AsyncSession` и Unit of Work короткоживущие: они создаются для одной
бизнес-транзакции, содержат её RLS-context, advisory lock и identity map, а
после awaited commit/rollback закрываются и не переиспользуются между
запросами. Синхронные финансовые расчёты без I/O остаются обычными функциями
application-слоя: async не применяется как замена CPU-вычислениям.

В одном execution path не смешиваются sync `Session` и `AsyncSession`.
Infrastructure-адаптеры внешнего I/O используют async API; blocking-библиотека
допускается только за явно выделенным адаптером, чтобы не блокировать event
loop.

Alembic migration job — исключение из runtime async-стека: Alembic выполняет
schema migrations синхронно через sync API того же драйвера `psycopg` 3. Job
работает до старта API-реплик и вне HTTP event loop, поэтому не создаёт
blocking-риска для пользовательских запросов.

Границу транзакции определяет бизнес-логика application-слоя. Handler или use
case явно решает, какие изменения должны пройти атомарно в одной транзакции и
когда нужен commit либо rollback. Presentation не вызывает `commit`/`rollback`
и не дробит бизнес-операцию на независимые записи; entity handler не может
обойти те же правила и транзакционные инварианты, что и use case.

Entity handler применяется к простой операции над одной сущностью. Use case
применяется, когда сценарий меняет несколько сущностей, содержит финансовый
инвариант, оркестрирует import/export или имеет внешний эффект. Это разделение
не меняет слой: оба типа компонентов живут в application и используют те же
DI-порты, owner scope и правила транзакций.

Application использует лёгкий CQS (Command–Query Separation). Query только
читает данные и не меняет состояние. Command меняет состояние и возвращает
лишь минимальный результат, нужный transport-слою: например, `id`, `version`
или статус. Отдельные read/write БД, event sourcing и полный CQRS не вводятся.

Application и infrastructure сообщают об ошибках через типизированные
framework-neutral прикладные исключения: отсутствие сущности, конфликт версии,
нарушение инварианта, недопустимое состояние. Только presentation преобразует
их в HTTP-ответы и коды 404/409/422. `HTTPException` и HTTP-детали за пределами
presentation запрещены.

Pydantic-схемы используются в presentation для HTTP-валидации и сериализации;
application работает с command/query/result DTO. Отдельную transport-схему и
маппинг не создают ради полного дублирования: если application DTO совпадает с
HTTP-контрактом по всем полям и семантике, presentation может использовать его
напрямую. При отличии в полях, нормализации, валидации, секретах или
HTTP-метаданных создаётся явная presentation-схема/адаптер; application DTO не
получает зависимость от FastAPI.

Application DTO реализуются immutable `dataclass`/typing-объектами и не
зависят от Pydantic. Pydantic остаётся transport-инструментом presentation;
прямое использование DTO presentation-слоем не превращает DTO в Pydantic или
FastAPI-модель.

Целевая структура пакетов использует явные имена:

```text
app/presentation/    # FastAPI, CLI, Pydantic transport, DI composition
app/application/     # use cases, commands/queries, policies, ports
app/infrastructure/  # SQLAlchemy, PostgreSQL, Alembic, внешние адаптеры
```

Существующие `api`, `core`, `db`, `models` и связанные модули переносятся
инкрементально, сохраняя публичные контракты на каждом шаге. Новые backend
возможности создаются сразу в целевом слое; big-bang переименование запрещено.

Текущие модули `api/*` и часть `core/*` ещё смешивают эти ответственности;
переход выполняется постепенно по [TD-005](../../technical-debt.md). Новая
функциональность должна сразу следовать этой структуре.

## Не входит в это решение

- Включение нескольких реплик в production пока не завершено: остающиеся
  несовместимости перечислены в [TD-002](../../technical-debt.md). Это не
  отменяет требования совместимости для новой backend-функциональности.
- SQLite не поддерживается; его удаление из кода, тестов, контейнера и
  документации отражено в [TD-003](../../technical-debt.md).
- Текущие отдельные private budget databases заменяются общей БД по
  [TD-004](../../technical-debt.md).
- Отдельный frontend-hosting не требуется: same-origin раздача через FastAPI
  остаётся рабочим вариантом и при нескольких backend-экземплярах.
- Physical backup/restore PostgreSQL не является функцией backend. Остатки
  прежней реализации отражены в [TD-001](../../technical-debt.md).
- Мультивалютность не входит в backend-модель до отдельной миграции и ADR-001.

## Последствия

- Новые backend-функции добавляются в существующий FastAPI-монолит и должны
  использовать общие зависимости авторизации, CSRF, сессии БД и обработку
  ошибок.
- Изменение модели требует Alembic-миграции; если оно меняет схему, должна быть
  обновлена `docs/database-schema.excalidraw`.
- Новая backend-функциональность не должна добавлять process-local состояние,
  от которого зависит корректность запроса или данных.
- Финансовая мутация должна брать advisory lock с ключом из стабильного
  namespace и server-side `user_id`; глобальная блокировка на всех
  пользователей запрещена.
- Экспорт, импорт и сброс финансовых данных всегда scoped по владельцу;
  они не могут проверять пустоту, читать или удалять данные другого
  пользователя.
- Reset финансовых данных требует текущий пароль и фразу `RESET`, выполняется
  атомарно и оставляет audit-событие; учётная запись и возможность загрузить
  ZIP после reset сохраняются. Остальные сессии пользователя отзываются, а
  текущая сессия остаётся действующей.
- Новая backend-функциональность следует слоистой архитектуре: transport не
  обращается к SQLAlchemy напрямую, финансовые правила не зависят от FastAPI,
  а application use case или entity handler получает доступ к данным через
  DI-переданные порты и сам определяет атомарную транзакционную границу.
- Перед включением нескольких реплик нужно закрыть TD-002 и проверить
  миграционный rollout, shared rate limit и конкурентные финансовые мутации.
