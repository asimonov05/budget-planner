# Архитектура

## Контур развертывания

В production работают контейнер приложения с одним процессом Uvicorn и отдельный контейнер PostgreSQL. FastAPI обслуживает `/api/v1`, OpenAPI и собранную React SPA. Неизвестный API-маршрут возвращает JSON 404 и не перенаправляется на `index.html`; SPA fallback применяется только вне API.

PostgreSQL 17 хранит данные в named volume `postgres_data` и не публикует порт на хост. Единственная рабочая база `budget` хранит пользователей, сессии и финансы всех пользователей. Каждая финансовая строка имеет обязательный `user_id`. Backend берёт его из сессии и устанавливает transaction-local RLS-контекст до первого обращения к данным пользователя. Ограниченная runtime-роль `budget_runtime` не владеет таблицами; отдельные роли применяют миграции и дают владельцу диагностический read-only доступ к админке. Физический backup выполняется снаружи приложения.

```text
browser -> :8000 FastAPI/Uvicorn -> handlers/core -> SQLAlchemy -> PostgreSQL budget
                    |                                   RLS(user_id)
                    -> /app/static

Compose migrate job -> Alembic -> PostgreSQL budget
Host backup job -> pg_dump/pg_restore -> external storage
```

## Слои backend

ADR-002 задаёт целевое разделение presentation, application и infrastructure. Текущие маршруты и часть `core` ещё смешивают эти ответственности; план поэтапного переноса зафиксирован в [TD-005](technical-debt.md). Схемы Pydantic проверяют HTTP-данные, SQLAlchemy описывает persisted-модель, часть расчётного ядра содержит чистые детерминированные формулы.

Сброс собственного бюджета уже оформлен как `presentation/reset_budget.py` →
`application/reset_budget.py` → `infrastructure/reset_budget.py`: use case
определяет атомарную транзакцию, а HTTP-слой только собирает команду и
преобразует ошибки.

Самостоятельная регистрация аналогично проходит через
`presentation/registration.py` → `application/register_user.py` →
`infrastructure/register_user.py`. Создание учётной записи и сессии атомарно;
новый пользователь получает обычную роль и пустой личный бюджет. Форма
доступна всем посетителям приложения после локальной настройки владельца.

Финансовые операции, перевод, проведение плана, движения резерва, batch-редактирование и подтверждение импорта атомарны. Редактируемые сущности имеют версию; устаревшая запись получает HTTP 409. API поддерживает idempotency key для повторяемых команд; UI передаёт его для операций, переводов, сверки плана, целей и оплат кредита.

## PostgreSQL и миграции

Отдельный одноразовый Compose-сервис `migrate` применяет Alembic до запуска API; процесс приложения только проверяет текущую ревизию. Перед обновлением внешний оператор создаёт dump. Денежные поля используют PostgreSQL `BIGINT`.

Финансовые мутации берут PostgreSQL advisory transaction lock с ключом из фиксированного namespace и аутентифицированного `user_id`: операции одного пользователя сериализуются, разные пользователи не ждут друг друга. ORM добавляет фильтр владельца, PostgreSQL `FORCE ROW LEVEL SECURITY` повторно ограничивает строки, а составные внешние ключи запрещают связи между бюджетами. Для `sessions` действует отдельная RLS-политика: до определения пользователя она допускает поиск только по hash текущего токена; после аутентификации применяет owner scope. Канонический ZIP импортируется только в пустой финансовый контур текущего пользователя с переназначением внутренних ID. Оставшиеся SQLite-ветки и готовность к нескольким репликам отслеживаются в [реестре технического долга](technical-debt.md).

## Frontend и темы

React SPA хранит только локальные предпочтения интерфейса; финансовое состояние всегда приходит из API. Выбор темы имеет три значения: `light`, `dark`, `system`, а независимая цветовая схема — `forest`, `ocean`, `plum`, `amber`. Предпочтения сохраняются в `localStorage`; вычисленная яркость устанавливается атрибутом `data-theme`, а схема — `data-color-scheme` на корневом HTML-элементе.

Небольшой синхронный bootstrap в `index.html` применяет сохранённые значения до загрузки React и CSS-отрисовки. React-провайдер затем поддерживает `color-scheme`, `theme-color` и подписку на `prefers-color-scheme` для системного режима. Настройки не синхронизируются с сервером и не входят в бэкап или экспорт проекта.

## Offline и границы

После сборки нет CDN, удаленных шрифтов, телеметрии или внешней авторизации. У каждого пользователя приватный бюджет; совместная работа нескольких пользователей внутри одного бюджета пока не поддерживается. Несколько реплик приложения отдельно не тестировались; PostgreSQL не публикуется за пределы сети Compose.

## Безопасность контейнера

Runtime-пользователь приложения `budget` имеет UID/GID 10001. Его root filesystem read-only, временный каталог — ограниченный `tmpfs`, capabilities удалены, `no-new-privileges` включен. Каталог `.secrets` на хосте доступен только владельцу. Docker socket не подключается.
